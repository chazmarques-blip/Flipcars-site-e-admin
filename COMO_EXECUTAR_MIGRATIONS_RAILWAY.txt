💡 O QUE CADA PARTE FAZ:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

npm run migration:run  → Cria todas as tabelas no banco (users, leads, etc.)
                          Executa todos os arquivos em backend/src/database/migrations/
                          
&&                     → Se a migração der certo, executa o próximo comando
                          Se der erro, para aqui e não executa o resto
                          
npm run seed           → Popula dados iniciais no banco
                          Cria o usuário superadmin
                          Executa backend/src/database/seeds/
                          
&&                     → Se o seed der certo, executa o próximo comando
                          
npm run start:prod     → Inicia o backend em modo produção
                          Abre na porta 3001
                          Fica rodando e aceitando requisições

❓ PERGUNTAS FREQUENTES:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q: Preciso rodar as migrations toda vez que faço deploy?
A: Não! Depois que rodar uma vez, você pode voltar o Start Command 
   para apenas "npm run start:prod". As migrations só precisam rodar
   uma vez para criar as tabelas.

Q: E se eu adicionar novas migrations no futuro?
A: Aí sim, você muda o Start Command de novo temporariamente para incluir
   "npm run migration:run" antes do start:prod.

Q: O que acontece se eu rodar as migrations duas vezes?
A: Nada! O TypeORM é inteligente e não vai rodar migrations que já foram
   executadas. Ele mantém um histórico no banco.

Q: Posso testar localmente antes de fazer no Railway?
A: Sim! No seu ambiente local com o banco PostgreSQL rodando:
   cd backend
   npm run migration:run
   npm run seed
   npm run start:dev

Q: Como desfazer uma migration?
A: Use o comando: npm run migration:revert
   Mas cuidado, isso apaga dados!

Q: O seed pode ser executado múltiplas vezes?
A: Depende de como foi escrito. O seed do superadmin tem proteção para
   não criar duplicatas. Mas em geral, seeds são feitos para rodar uma vez só.

🔧 TROUBLESHOOTING:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PROBLEMA: Deploy falha com erro "Cannot find module"
SOLUÇÃO: Verifique se o comando foi copiado corretamente, sem caracteres extras.

PROBLEMA: Migration falha com "relation already exists"
SOLUÇÃO: As tabelas já existem! Isso é OK. Mude o comando de volta para só
         "npm run start:prod".

PROBLEMA: Seed falha com "duplicate key value"
SOLUÇÃO: O superadmin já foi criado! Isso é OK. Mude o comando de volta para
         só "npm run start:prod".

PROBLEMA: Backend demora muito para subir
SOLUÇÃO: Migrations podem demorar 1-2 minutos. Seja paciente! Veja os logs.

PROBLEMA: Logs mostram erro de timeout
SOLUÇÃO: O Railway tem limite de tempo para build. Se as migrations forem muito
         grandes, considere rodá-las separadamente via Railway CLI.
